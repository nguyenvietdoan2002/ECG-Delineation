# Decision log

Decisions agreed on 2026-10-09 while planning step 1. The plan itself is in [plan.md](plan.md).

| # | Decision | Why |
|---|---|---|
| 1 | TimesFM 3 is a frozen backbone with a trained head. | TimesFM only forecasts; it cannot delineate without a trained head. |
| 2 | The goal is research and a publishable result. | We want evidence for or against TimesFM, not a product yet. |
| 3 | Signals are 10 s, 12-lead, 500 Hz resting ECGs. | This matches LUDB (and later MIMIC-IV-ECG). |
| 4 | Output uses NeuroKit2's keys, per beat and lead. | It is a drop-in replacement for `nk.ecg_delineate`. |
| 5 | The model predicts per-sample regions (P/QRS/T/none), and points are derived from them. | This is the standard target in LUDB papers and is easy to train. |
| 6 | Code lives in a new project, `Meddies/ecg-delineation/`. | `Meddies/timesfm` is a clone of upstream google-research/timesfm. |
| 7 | Rigor is publication-level: fixed person-level splits, seeds, CIs, and this log. | Rigor costs little up front, and LUDB is small enough that single splits vary a lot. |
| 9 | TimesFM 3 is the only foundation model; we use neither 2.5 nor ECG-FM. | This was the user's choice. The non-commercial licence is accepted. |
| 10 | TimesFM runs two passes, forward and time-reversed. | TimesFM is causal, so wave ends need right-hand context. |
| 11 | Step 1 trains and tests on LUDB only, plus a learning curve. | MIMIC has no expert labels. The learning curve shows whether more data would help. |
| 12 | Input stays at 500 Hz. | LUDB is recorded at 500 Hz, so no resampling is needed. |
| 13 | We compare TimesFM 3, NeuroKit2 and a U-Net control. | Without a trained control, a win over NeuroKit2 cannot be credited to TimesFM. |
| 14 | The NeuroKit2 baseline is `prominence` only. | It is NeuroKit2's best-scoring method on LUDB (Emrich et al. 2024). |
| 15 | The primary metric is error SD at the five CSE points, with F1 at ±150 ms as a safeguard. | F1 at 150 ms is saturated, and the SD separates methods. It was fixed before any run. |
| 16 | TimesFM takes all 12 leads together. | Multi-lead input uses TimesFM 3's variate attention. |
| 17 | The U-Net also takes all 12 leads. | Both get equal information, so the only difference is TimesFM. |
| 18 | ECG-FM is not used. | This was the user's choice. |
| 19 | The main head is a small conv head over neighbouring patches; a linear probe is also reported. | The conv head uses context but stays smaller than the U-Net. The probe shows what the states hold on their own. |
| 20 | Step 1 includes the U-Net. | The stop rule needs it. |

Implementation-stage decisions, agreed on 2026-10-10:

| # | Decision | Why |
|---|---|---|
| 21 | Local git repo, one commit per step, no remote yet; a tagged "frozen" commit before the final runs. | Every number traces to code that could not have been tuned after seeing test results. |
| 22 | Built milestone by milestone, test-first, with a report after each (M0–M4). | Same workflow as `ecgrepro`; checkpoints without slowing every file down. |
| 23 | Order: M0 foundations → M1 scorer + NeuroKit2 → M2 states → M3 fold-0 models → M4 final runs. | The scorer is checked against Emrich 2024's published NeuroKit2 numbers before any model is trained. |
| 24 | Crop each lead to 4992 samples (156 blocks); no padding. NeuroKit2 gets the full 5000. | 5000 is not a multiple of 32; padding would misalign the forward and reversed passes. No mark lies after sample 4832. |
| 25 | No data augmentation for either trained model. | The stop rule asks whether TimesFM adds something given the same data. |
| 26 | No hyperparameter search; fixed settings table, developed on fold 0's validation people only. | Neither model is tuned harder than the other; nothing is chosen after a test result. |
| 27 | Main head: layer blend, 2560 → 128, three width-3 convolutions, 128 → 32 × 4 (≈ 0.49M). Probe: layer blend + one linear layer. | Context of ±3 blocks without becoming a second U-Net; always smaller than the U-Net (≈ 2M). |
| 28 | Stop rule tested by paired bootstrap over people (10,000 draws, 95% interval of the difference). | Both models are tested on the same people; non-overlapping intervals would be needlessly harsh. |
| 29 | Every experiment step runs on Modal (CPU and T4 GPU functions), not the local GPU. | One consistent environment; the laptop GPU is power-throttled to a fraction of its speed; fits the $30/month free credit. |
| 30 | Store all 20 layers in fp16 in the Modal Volume (36.6 GB); delete after the final runs. | Containers can hold a fold's states in RAM, so the spec's 20-layer blend stands. Probe showed fp16 is safe. |
| 31 | All heads for one fold train jointly in one container over a single data stream. | RAM-hours cost as much as the GPU; loading 29 GB once per fold instead of per run keeps heads at a few dollars. |
| 32 | T4 GPUs for everything; no per-launch cost check; credits reported at milestone ends. | The workload is small; T4 is the cheapest adequate GPU. User's choice on the check. |
| 33 | `timesfm3` is imported from `Meddies/timesfm/src` via a `.pth` file locally and copied into the Modal image. | An editable install would write an `egg-info` folder into the upstream clone. |

Implementation details fixed during M0 (2026-10-10):

| # | Decision | Why |
|---|---|---|
| 34 | A wave's label covers onset..offset inclusive; the mask covers first mark..last mark inclusive. | LUDB's `)` marks the last sample of the wave. |
| 35 | For an incomplete wave (peak without onset or offset) the whole gap between the neighbouring complete waves is masked out. | Its true extent is unknown; masking only the known side would teach a wrong boundary. 134 such waves in LUDB. |
| 36 | Rhythm groups for stratification: `sinus` (any "sinus" rhythm), `af_flutter`, `other`. LUDB has 182 / 18 / 0. | Only two groups occur; AF/flutter is the hard case and must appear in every test fold (3–4 people each). |
| 37 | Folds are dealt round-robin per rhythm group with one running counter; validation (20%) and learning-curve subsets (25%, 50%) are stratified the same way; subsets are nested prefixes of one shuffle, taken from the training people with the validation people held fixed. | Balanced fold sizes (40 each), every subset keeps AF people, and early stopping is comparable across subset sizes. |
| 38 | `splits/ludb_5fold_seed0.json` was generated locally (deterministic, seed 0) and committed; experiments read the file, never regenerate it. | A 20-second deterministic job; the file is the single source of truth on both laptop and Modal. |
| 39 | Local environment uses CPU PyTorch; the Modal image installs PyTorch 2.14.1 with CUDA 13 and copies `timesfm3` and `ecgdelin` from the local checkouts at run time. | The laptop only runs unit tests; Modal always runs the exact code in the working tree. |

Decisions for M1 (scorer and NeuroKit2 baseline), agreed on 2026-10-10:

| # | Decision | Why |
|---|---|---|
| 40 | Predicted regions are grouped into beats the way NeuroKit2 reports them: one entry per QRS, the nearest P region before it and the nearest T region after it. P or T regions with no QRS neighbour in their interval are orphans: dropped from the output and counted. | NeuroKit2 can only report waves attached to a detected R peak, so all methods are scored on the same kind of output. The orphan count keeps the loss visible. |
| 41 | One-to-one matching is greedy, nearest pair first, within the tolerance window (inclusive). The strict ±40 ms figures come from a separate matching run at that tolerance. | Deterministic and simple; beats are far enough apart that it equals optimal assignment in practice. |
| 42 | A NeuroKit2 exception on a lead counts as no predictions for that lead; its marks are misses. The number of failed leads is reported. | A real user gets nothing from an exception. Excluding failed leads would flatter the baseline. |
| 43 | Sanity band for the Emrich 2024 lead-I check: F1 within 1 percentage point and each error SD within 3 ms. Beyond that, M1 stops for investigation. | Matching details and the incomplete-wave rule can move numbers by that much; anything larger points to a scorer bug. |
| 44 | Nine point types are scored (P, QRS, T onsets, peaks, offsets; LUDB's QRS peak against `ECG_R_Peaks`); Q and S are produced but not scored. Unmatched predictions outside the marked span or inside a masked gap are ignored, but a prediction there may still match a mark at the span's edge. Error = prediction − reference in ms. Within-recording SD is taken per recording and lead, then averaged. NeuroKit2 runs over all 200 records on Modal CPU; its predictions and results JSON are committed under `results/`. | LUDB has no Q or S marks. Without the edge rule, a prediction a few samples late for the last T offset of a lead would be lost and the mark counted as a miss, biasing T offset and P onset sensitivity by up to one beat in ten. The rest keeps the scorer identical for every method and the baseline reproducible from the repo. |
| 45 | Error SDs are population SDs (divide by N) over matched pairs. | With tens of thousands of pairs the choice is immaterial, and the population form makes the pooled SD exactly decomposable into per-person sums, which the paired bootstrap resamples. |
| 47 | Decoder QRS peak = the highest positive deflection from the region's baseline when it exceeds 0.02 mV, else the nadir. P and T peaks stay the largest absolute deflection. Chosen on fold 0's validation people only. | LUDB marks the R wave even when the S wave is far deeper (rS in V1–V3, aVR, III). The absolute-deflection rule disagreed with the marks by over 20 ms for 34% of QRS peaks on those people; this rule for 4%. P and T peaks already agreed for 97%. |
| 46 | The Emrich 2024 sanity check compares our lead-I within-recording SD and pooled mean against their single-lead rows, and also runs a paper-faithful variant with FastNVG R-peaks (`ecg_peaks(method="emrich2023")`) for that check only. The baseline itself keeps NeuroKit2's default R-peak detector (decision 14 and story 23). | The paper's σ is the average of per-record SDs and its R-peaks came from FastNVG, so a like-for-like check needs both; the baseline stays what a NeuroKit2 user gets by default. See `docs/references.md`. |

| 48 | Outcome of the Emrich 2024 check (2026-10-10): lead-I mean and within-recording SD agree with the paper within 0.3 ms for all nine points, and F1 within the band for the six QRS and T points. P-wave F1 is 91.8% against 99.8%: of our 247 lead-I P-onset false positives, 191 are in the 18 AF/flutter people (no P waves exist; `prominence` reports one per beat) and 51 are at sinus beats where the cardiologists marked no P in lead I; only 3 P onsets are missed. The scorer's false-positive rule stands; the band is treated as met for the scorer. | The differences are confined to false-positive counting on beats without a P annotation, which the paper evidently did not count; matching and error computation are reproduced to a fraction of a sample. Reporting a P wave during atrial fibrillation is a real delineation error, and the trained models are judged by the same rule. |

| 49 | The FastNVG variant (`ecg_peaks(method="emrich2023")`, decision 46) is reported in `results/neurokit_prominence_emrich2023.json` but not used further; the Emrich 2024 check rests on the default-detector run. | In NeuroKit2 0.2.13 that detector misses 7% of QRS in lead I and 36–57% in V1–V3 (QRS F1 79% over all leads against 98.5% for the default detector), so it does not reproduce the paper's pipeline, whose R-peak F1 was 99.8%. Diagnosing NeuroKit2's port is out of scope. |

Implementation details fixed during M2 (2026-10-10):

| # | Decision | Why |
|---|---|---|
| 50 | TimesFM is called through its full-sequence `forward` with the 12 leads as variates, 156 patches of 32, no masks, and `patch_is_target` True for every lead; no detrending, no CPM mask. Each layer's output is captured with forward hooks on `transformer_stack.layers`. | This is how TimesFM's own `decode` presents target series: the model sees each block's values but not the rolled "future covariate" copy of what follows, so forward states stay causal. `forward` skips `decode`'s padding and linear detrending; the 0.5 Hz high-pass handles drift. |
| 51 | The high-pass uses mirrored ("even") padding of 6 s. | scipy's default pad of a few dozen samples is far shorter than a 0.5 Hz filter's memory; a probe on a 10 Hz wave showed the end transient falls from 1.9% to 0.5% of the amplitude 1 s from the ends and to 0.2% at 2 s with this choice. Edge transients cannot be removed entirely. |
| 52 | States are stored per recording as `/vol/states/<checkpoint sha>/<record>.npy`, fp16, shape (20, 12, 156, 2560) laid out as [forward 1280 | reversed 1280], with a manifest; the checkpoint sha comes from the Hugging Face snapshot folder. | One file per recording keeps a fold's loading simple; the sha key invalidates the cache if the checkpoint changes (spec). |
| 53 | The `gpu`-marked tests are deselected locally (`addopts = -m 'not gpu'`) and run inside a T4 container through `scripts/gpu_tests.py`, which mounts `tests/` into the image. | The laptop must never download the 1.3 GB weights or run the backbone; the same test files run unchanged on Modal. |
| 54 | M3 is lean: one seed each of the linear probe, the main head and the U-Net on fold 0, trained jointly in one T4 container and scored on fold 0's 32 validation people only. The per-layer probes and the forward-only ablation move to M4. No test fold is scored before the frozen commit. | The code is the same as M4's, so a fuller M3 would only add credits and the temptation to look; one seed is enough to show that everything trains. Decision 26 is honoured by never seeing a test result before the freeze. |
| 55 | The U-Net standardises each lead of each recording (zero mean, unit variance over the 4992 samples) inside its forward pass; the heads receive the stored states. | TimesFM normalises each lead internally, so this puts both trained models on an equal footing; raw millivolts would make the U-Net depend on gain differences between leads. |
| 56 | The layer blend normalises every layer's 2560-vector (zero mean, unit variance over the features, no learned affine) before the softmax-weighted sum, as in ELMo's scalar mix. | Residual-stream magnitudes grow with depth (max abs state 1080), so raw states would let the deep layers dominate the mix whatever the weights, and the first linear layer would see inputs of very different scales. The normalisation has no parameters, so the head stays at 0.49M. |
| 57 | U-Net: channels 16, 32, 64, 128, 256 (five levels, four max-pools, 312 samples at the bottom), two Conv1d(kernel 9)-BatchNorm-ReLU blocks per level, transposed-convolution upsampling with skip concatenation, a 1x1 output convolution to 12 x 4 maps, no dropout; about 1.9M parameters. | The plan fixes five levels, 16 to 256 channels, kernel 9 and about 2M parameters; these are the standard choices that fill in the rest. |
| 58 | Training mechanics: samples outside the mask get target -1 and are ignored by the cross-entropy; the validation loss is the mean cross-entropy over all valid samples of the validation people; all models of a fold train in one loop over one data stream, each with its own AdamW and its own early stopping (patience 20 on validation loss, best weights restored); every model, optimiser and the shuffling RNG are checkpointed to the Volume after each epoch and resumed after a preemption; predictions are argmax -> decoder -> scorer, with peaks read from the high-passed 4992-sample signal the models saw. | Implements the training table and spec stories 25a and 25b; a resumed run reproduces the uninterrupted one, which a test checks. |
| 59 | The M3 report puts the three trained models next to NeuroKit2 on the same 32 validation people (NeuroKit2's predictions come from the M1 run) and includes exploratory stop-rule verdicts on those people. None of it is a result of the study. | A side-by-side on the development people is the sanity check; it is labelled validation-only so nobody mistakes it for the pre-registered comparison. |

Decisions after the M3 review, agreed on 2026-10-11:

| # | Decision | Why |
|---|---|---|
| 60 | The M3 fold-0 development results are followed by a deep-dive report on the validation people, generated by a script into `docs/m3-report.md` with figures under `results/m3/`: per-lead and per-person errors, orphans split into edge waves and fragments, the QRS-peak bias shared by the trained models, behaviour on the AF people, beat overlays of marks and predictions, and the probe's versus the head's layer weights. Any fix it suggests to the decoder or labels needs the user's approval and a log entry before the freeze. | The freeze is the last point where something learned from development outputs can be acted on legitimately; a generated report keeps every number reproducible. |
| 61 | The forward-only ablation, the per-layer probes and the learning curve are removed from step 1 (plan "Ablations" and "Learning curve"; spec stories 8, 20 and 21). They may be run as a separate step after the stop-rule verdict. The nested subsets stay in `splits/`. | The stop rule needs only the head, the probe and the U-Net; which ablation is worth its credits depends on the verdict. User's choice. |
| 62 | The U-Net and head recipes are frozen as M3 ran them; no development-stage change to either. | On fold 0's validation people the U-Net's within-recording SDs and F1 are in the published LUDB range, and its pooled SDs are below Moskalenko et al.'s (arXiv 2001.04689) on every CSE point, so the control is credible; an equal pre-registered budget is easier to defend than a control tuned harder. |
| 63 | The stored states are kept after the final runs (amends decision 30). | Storage under 1 TiB is free; a step 2 would need the same states, and re-extraction would need re-verification. |
| 64 | How the verdict aggregates: every person's predictions come from the models of the fold that held them out, so all 200 people are pooled; in each bootstrap draw the primary metric is computed per seed and averaged over the 3 seeds; the F1 safeguard uses the same draws; the five per-fold differences are reported for information only; NeuroKit2 is compared from its M1 run on the same people. | Per-fold averaging leaves five correlated numbers (Nadeau and Bengio 2003; Varoquaux 2018) and F1 averaged over folds is biased (Forman and Scholz 2010); pooling is what the plan already pre-registered. |
| 65 | Order before the freeze: deep dive, approved fixes, M4 code with tests (multi-seed joint trainer, test-fold prediction, cross-run aggregation and verdict, report generator), a two-epoch rehearsal of the whole pipeline on fold 0, the tag `step1-frozen`, then the final runs with the tag's commit in every JSON; afterwards only logged bug fixes. The five fold containers run detached, in parallel. Estimated cost about $10; credits sufficient as of 2026-10-11. | A scoring bug found after the real runs would force a re-run or an unlogged fix. |
| 66 | Outputs: `docs/report.md` generated from the result JSONs with figures, and `docs/paper.md` in Markdown, methods drafted during the runs and results after the verdict, converted to LaTeX once a venue is chosen. | Every number stays traceable to a JSON; the methods section follows from this log. |
| 67 | Outcome of the M3 deep dive (2026-10-11, `docs/m3-report.md`): CPU re-inference and local scoring reproduce the stored predictions and the JSON exactly; orphans are almost all unscored edge waves (U-Net 708 of 714, head 220 of 228), none unanchored; the +3 ms QRS-peak mean error is the decoder's and comes from LUDB's marks, which sit one sample before the signal's extremum for about 70% of QRS beats; stricter R-wave rules are worse in every lead, so decision 47 stands; P and T peak rules stand. Labels, decoder and scorer are left unchanged for the freeze. The user chose to leave the decoder's peaks as they are rather than shift them one sample to match LUDB's convention; the offset will be stated in the paper. | The peaks are not in the primary metric, the offset is an annotation convention, the mean error is reported anyway, and a post-hoc shift would be a hand-made correction, not something the model learned. |

| 68 | The freeze (2026-10-11): the tag `step1-frozen` marks the commit that adds the M4 code, after the two-epoch rehearsal `m4_fold0_smoke` ran the whole chain (nine models trained jointly, test fold streamed, pooled scoring, verdict, report). The code changes since M3, all behaviour-preserving for the pre-registered metric: the trainer normalises each batch's layers once for every head (identical results, tested); three seeds per fold train as nine trainees in one container with one shuffled data stream (decision 31) and the test people are read only after training; the scorer gains `compare_seeds` and `seed_averaged_primary` (the metric per seed averaged inside each draw, decision 64), `errors_by_lead`, and a subgroup primary over the points the subgroup has (AF people have no P marks); `crossval.assemble` refuses gaps and duplicates; `scripts/final_report.py` writes `docs/report.md` and `results/m4/summary.json`. Rehearsal timings: states loaded in 34 s, 9 models at about 45 s per epoch, 40 test people in 48 s, 4.7 GiB of GPU memory. After this tag only logged bug fixes. | Decision 65. Every number of the final runs traces to this commit. |

| 69 | Launch of the final runs (2026-10-11, after the tag; tooling only, no change to the frozen code): the app is deployed with `modal deploy` and the five folds are spawned on the deployed function by `scripts/launch_m4.py`, which exits at once; `scripts/train_fold.py::fetch` copies each finished run's files from the Volume. A first launch with `modal run --detach ... --folds 0,1,2,3,4` was stopped within minutes, before any container had finished loading its states, after Modal warned that detached mode keeps only the last spawned function alive once the client disconnects. The runs record `git step1-frozen`. | A waiting client was a single point of failure for four of the five folds; the deployed calls are independent of any client. |
